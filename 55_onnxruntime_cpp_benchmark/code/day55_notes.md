## 6. 两种计时边界

### 6.1 纯运行时模式 `runtime-only`

输入张量在计时前已经准备完毕，计时器内部只有：

```text
Ort::Session::Run
```

图片解码、预处理、Session 创建、Top-k、控制台输出和 CSV 写入均不计时。

### 6.2 端到端模式 `end-to-end`

计时器包含：

```text
cv::imread
→ OpenCV 缩放、裁剪与归一化
→ 组装 batch 张量
→ Ort::Session::Run
→ 提取 Top-k
```

路径发现、Session 创建、控制台输出和 CSV 写入仍然不计时。

两种模式的数字不能混写成同一种延迟。

## 8. 先通过正确性门，再解释速度

性能结果生效前必须满足：

1. 所有 logits 都是有限数值；
2. 输出形状为 `[batch, 50]`；
3. 相同输入下，Day55 与 Day54 的最大 logits 绝对误差不超过 `1e-6`；
4. Top-1 和有序 Top-3 与 Day54 一致；
5. batch=1、3、6 都能实际运行。

如果正确性门失败，即使程序更快，性能结果也无效。

## 12. 最终阶段发现并修正的计时问题

最终复核发现：第一版 `runtime-only` 实现把 `Ort::Value` 输入张量创建和 logits 复制也放进了计时器，这不符合阶段一规定的“只测 `Session::Run`”。因此第一轮阶段三性能结果被作废，没有写入最终结论。

先增加回归测试，要求程序输出：

```text
Timed boundary: Session::Run only
Input tensor creations: 1
```

测试在修复前按预期失败。随后完成以下修正：

- 输入张量在预热和正式计时前只创建一次；
- 保证准备好的张量在全部运行期间有效；
- 计时器只包围 `Session::Run`；
- 最后一次 logits 的复制与检查放到计时器外；
- `end-to-end` 仍按合同在每次运行中完成解码、预处理、张量创建、推理与 Top-k。

最终复核还发现 Session 创建时间虽然打印到了控制台，却没有保留到 CSV。第二个回归测试先要求汇总 CSV 必须包含正数 `session_creation_ms`，测试失败后再补充实现。

两项修正完成后，全部测试重新通过，并重新运行12组实验覆盖旧结果。

## 13. 最终性能结果

每组先预热3次，再进行10次 Release 正式测量。`intra_threads=0` 表示使用 ONNX Runtime 默认的算子内线程配置。

| 模式 | Batch | ORT 算子内线程 | Session 创建 ms | 中位数 ms | P90 ms | 吞吐量 images/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| runtime-only | 1 | 1 | 88.1051 | 29.0812 | 29.3000 | 34.5337 |
| runtime-only | 1 | 0 | 94.6227 | 10.2033 | 10.5410 | 104.8362 |
| runtime-only | 3 | 1 | 87.1056 | 86.7707 | 87.3073 | 34.8990 |
| runtime-only | 3 | 0 | 96.8920 | 26.6537 | 28.7428 | 115.8049 |
| runtime-only | 6 | 1 | 86.1022 | 173.9199 | 177.7258 | 34.5044 |
| runtime-only | 6 | 0 | 93.7465 | 49.0900 | 55.6059 | 126.5971 |
| end-to-end | 1 | 1 | 87.3064 | 32.2024 | 32.5347 | 31.1404 |
| end-to-end | 1 | 0 | 96.2080 | 11.9218 | 13.0577 | 88.1509 |
| end-to-end | 3 | 1 | 85.8773 | 95.1852 | 97.6190 | 31.4746 |
| end-to-end | 3 | 0 | 98.6405 | 36.7619 | 39.3516 | 70.9980 |
| end-to-end | 6 | 1 | 92.6927 | 192.6930 | 193.2895 | 31.2232 |

## 14. 结果分析

### 14.1 默认线程与单线程

在本次所有组合中，ORT 默认线程配置都快于固定1线程。

- 纯运行时 batch=1：中位延迟从 `29.0812 ms` 降至 `10.2033 ms`；
- 纯运行时 batch=6：吞吐量从 `34.5044` 提升到 `126.5971 images/s`。

这不代表默认线程永远最优，只能说明它在本机、本模型和本次 CPU 实验中优于固定1线程。

### 14.2 Batch 变化

使用 ORT 默认线程时，纯运行时吞吐量随 batch 增大而上升：

```text
batch 1：104.8362 images/s
batch 3：115.8049 images/s
batch 6：126.5971 images/s
```

端到端吞吐量没有单调上升。batch=3 使用前3张图片，batch=6 使用全部6张，其中包括需要大幅放大的 32×32 图片和较大的 614×419 PNG。因此端到端 batch 对比同时混入了不同的解码和预处理工作量，不能被解释为纯粹的 batching 曲线。

### 14.3 解码与预处理开销

在 ORT 默认线程配置下，端到端中位数减去纯运行时中位数约为：

| Batch | 额外中位耗时 |
| ---: | ---: |
| 1 | 1.7186 ms |
| 3 | 10.1083 ms |
| 6 | 25.6817 ms |

这部分包含图片解码、缩放裁剪、归一化、batch 组装和 Top-3，并不只是 OpenCV 缩放时间。

### 14.4 Session 创建开销

12个独立进程中的 Session 创建时间为 `85.8773～98.6405 ms`。该时间被单独记录，没有混入两种推理计时。

长期运行的程序通常应该创建并复用 Session，而不是每处理一张图片就重新加载模型。

## 15. Day55 能证明什么

在本次受控 Release/CPU 实验中，可以证明：

- 两种计时模式和线程配置保持相同 logits；
- 纯运行时与端到端计时边界能够被严格分开；
- ORT 默认线程配置在本机优于固定1线程；
- 在已测试范围内，batch 增大提高了纯运行时吞吐量；
- 原始数据和汇总统计可以通过代码重新生成。

## 16. Day55 不能证明什么

本节不能证明：

- ORT 默认线程数就是最优线程数；
- batch=6 是所有 batch 中的最优值；
- C++ 比 Python 更快，因为没有进行公平的 Python 基准；
- CPU 结果可以代表 GPU、TensorRT、量化、嵌入式或能耗表现；
- 6张测试图片代表真实部署数据分布；
- 模型准确率、外部泛化或未知类拒识得到了改善；
- 10次测量能在所有系统负载下建立统计显著性。

本实验执行顺序固定，没有随机化或交错执行，也没有记录 CPU 频率、后台负载、内存占用和能耗。这些都是结论边界。

## 19. 今日关键记忆点

1. 性能测试前必须先定义计时边界。
2. `runtime-only` 的准备张量必须位于计时器外。
3. 模型与 Session 创建属于独立的生命周期成本。
4. 解释速度前必须先通过正确性等价门。
5. 预热结果不参与统计，正式结果必须全部保留。
6. 中位数和 P90 描述的是不同部分的延迟表现。
7. Batch 延迟、平均单图延迟和吞吐量是不同指标。
8. 线程默认值是实验条件，不是永远最优的结论。
9. 端到端 batch 对比可能受到不同图片解码负载干扰。
10. 部署性能优化不会自动修复模型泛化问题。
