# Day60：农业机器人作物行数据可行性审查

> 2026-09-05原位补充：Day59合同升级为多作物行与行间走廊后，对CRDLD全部1,930张
> 标签增加多行可分离性审计。原有许可、来源、重复、负样本和证据角色结论不变。

## 1. 今天完成了什么

Day60 没有急着训练模型，而是回答一个更靠前的问题：现有公开数据能不能支撑 Day59 已冻结的任务和“内部、外部都要经得住检查”的证据要求。

今天完成的链路是：

```text
候选源核验
→ 官方页面、许可、下载方式与任务视角检查
→ 下载一个可控的小包
→ 校验归档哈希
→ 检查图像/标签配对、解码、尺寸、标签值与重复
→ 设计 ID / OOD开发 / 冻结外部角色
→ 执行数据门禁
```

Day60 学习任务已完成；项目门禁结论是：

```text
DAY60_DATA_VIABILITY_BLOCKED
```

这两个结论并不矛盾。“学习完成”表示审查过程和笔记已经做完；`BLOCKED` 表示证据不足，不能进入环境与算法开发。

## 2. 为什么数据审查比立刻写算法更重要

前三个项目出现过内部效果好、外部泛化明显下降的问题。其根因不一定是模型太弱，也可能是：

- 同一视频的相邻帧被随机拆到训练和测试；
- 同一田块、日期或相机同时出现在两边；
- 官方 Test 只是同源测试，并不是独立外部数据；
- 数据全部包含目标，却没有“应该拒绝”的负样本；
- 图像视角与真正部署视角不同；
- 标签能做分割，却不能计算项目承诺的位置和方向指标。

所以数据可行性不是“能下载、能打开”就通过，而是要证明数据能支撑任务、指标和声明。

## 3. 五个候选的审查结果

### 3.1 CRDLD v2.1：最匹配的 ID 候选，但当前阻断

官方仓库：<https://github.com/JunfengGaolab/CropRowDetection>
官方下载：<https://lcas.lincoln.ac.uk/nextcloud/index.php/s/Eip4nWbetxJQ6No>

它描述了 2000 张图像、50 个组合条件、每图对应掩码和 `.mat` 线坐标，场景含阴影、杂草、不同生长期、断行、弯曲/坡度和轮胎印。拍摄来自地面机器人，视角与目标契约最接近。

但不能现在就把它当作合格 ID 数据：

1. GitHub 仓库没有展示数据许可证；
2. 官方划分按类别组织，未给出田块、日期、相机和连续序列键；
3. v1 说明基础图像经裁剪/旋转扩增，说明必须追溯到基础图像后再分组；
4. 没有地头、无行、非农田等应拒绝负样本。

结论：`BLOCKED_PENDING_LICENSE_PROVENANCE_AND_NEGATIVES`。

### 3.2 CCRDNet：标签和许可清楚，但视角不等价

官方下载：<https://zenodo.org/records/15194034>

Zenodo 元数据给出 CC BY 4.0、6.4 GB 归档和 MD5。论文描述 8 种作物、中央行三类掩码和方向误差评价。

但论文也说明图像全部由手持 Honor V30 Pro 在哈尔滨拍摄，相机高度和角度不限制；每张图又被人工确认存在中央行。因此：

- 它能帮助研究跨作物、光照和拍摄角度的 OOD 行为；
- 它不能代替“地面机器人固定前视相机”的主数据；
- 它不能评价 `reject`，因为没有无中央行负样本；
- 归档没有发现可直接使用的田块/日期/序列分组清单。

结论：只保留为 OOD 开发候选，不能充当冻结外部。

### 3.3 Bonn Multi-Crop：最合适的冻结外部候选，但尚未拿到

项目页：<https://github.com/Agricultural-Robotics-Bonn/visual-multi-crop-row-navigation>

README 描述了 5 种真实作物、3 个模拟田块、BonnBot-I、55°–75° 相机倾角，以及底边位置和方向标注。这与 Day59 指标高度一致，而且来源独立于 CRDLD。

但是数据需邮件联系作者申请。代码仓库采用 BSD-2-Clause，不等于单独提供的数据也自动采用同一许可。在未取得数据、许可和文件级分组前，它只能是候选。

结论：`BLOCKED_PENDING_AUTHOR_ACCESS_AND_DATA_LICENSE`。

### 3.4 Zenodo 18700580：已经下载并实审，只作 pilot

官方下载：<https://zenodo.org/records/18700580>

它是今天唯一完整下载并检查的数据包。审查时的归档路径为：

```text
D:\DL_code\data\crop_row_perception\sources\zenodo_18700580\S1_File.zip
```

完成 MD5 校验与解压审查后，原始压缩包已按用户要求删除；80 对解压样本仍保留在 `extracted\S1_File\`。

元数据许可为 CC BY 4.0，归档大小 49,731,314 字节。官方 MD5 与本地计算均为：

```text
79d2b2327e2389da496be8a40d6db415
```

元数据说明它混合作者在固安拍摄的玉米图像和公开 CRBD 子集。这个混合本来可以帮助做跨来源检查，但压缩包没有逐文件来源或序列表，所以不能可靠地把文件分成独立角色。

### 3.5 CWFID：合法可用，但任务不匹配

官方页：<https://github.com/cwfid/dataset>

CWFID 有图像、植被掩码和作物/杂草标注，并明确限制为非商业研究用途。它主要是近俯视作物/杂草识别数据，不提供本项目需要的前视中央行位置和方向标签。

结论：不因“农业图像”这个表面相似点把它强行放进证据链。

## 4. 对已下载 80 对样本做了什么检查

审查器位置：

```text
60_crop_row_data_viability/code/day60_data_audit.py
```

### 4.1 配对与可读性

结果：

```text
images = 80
masks = 80
missing_images = 0
missing_masks = 0
decode_failures = 0
shape_mismatches = 0
```

这证明压缩包完整、图像与同名掩码可读取，但只属于最低技术门槛。

### 4.2 分辨率分组

```text
320x240   : 48 对
3840x2160 : 11 对
1024x576  : 21 对
```

三个明显分辨率簇提示数据来源或采集设备不同。分辨率可以作为调查线索，但不能替代官方来源/序列标识。

### 4.3 标签值不统一

不同掩码分别出现：

```text
0,1,2 : 42 张
0,2   : 6 张
0,255 : 11 张
0,1   : 21 张
```

因此后续若做 pilot，必须按来源显式映射标签，不能假设所有掩码都是统一的 0/1 二值图。

### 4.4 重复检查

没有发现字节级完全重复的 JPG，但发现 4 组完全相同的 PNG 掩码：

```text
369–374
375–379
380–384
385–388
```

相同掩码不必然表示标注错误，也可能是相邻画面共用同一几何真值；但它明确说明这些文件不能跨训练/测试随机分散。没有序列信息时，应把整个连续段视为同一泄漏组。

## 5. 今天实现的数据门禁

审查器要求选入正式证据链的每个数据源都满足：

- `available`：能实际取得；
- `license_verified`：数据许可明确；
- `task_match`：匹配地面机器人前视任务；
- `labels_support_metrics`：能计算近端位置和方向；
- `provenance_groups_known`：知道最高泄漏单位；
- `has_required_negatives`：能评价拒绝行为；
- 冻结外部还必须 `independent_of_id`。

同时必须具有 ID、OOD 开发和冻结外部三个角色。候选研究资料可设为 `selected_for_gate=false`，不会因为一个已否决候选而错误阻断真正合格的组合。

本次门禁输出 10 个阻断项，最终为：

```text
status = BLOCKED
```

## 8. 下一步怎样解除阻断

1. 向 CRDLD 作者确认数据许可、基础图像到增强图像映射，以及田块/日期/序列/相机键；
2. 向 Bonn 作者申请数据，同时询问数据许可和文件级分组；
3. 准备独立、合法的地头/无行/非农田/严重模糊/曝光失败负样本；
4. 获得数据后重新检查损坏、配对、标签值、重复/近重复和跨角色重叠；
5. 只有数据门禁明确通过，才允许进入环境门禁。

## 9. 今天真正学到的关键点

- 数据可下载，不等于数据可用于声明；
- 仓库许可证，不自动等于另行提供的数据许可证；
- 官方 Test，不自动等于独立外部测试；
- 不同分辨率，只是来源线索，不是可靠分组键；
- 完全相同掩码和连续文件名会暴露随机拆分风险；
- 只有正样本，无法验证拒绝系统；
- 诚实的 `BLOCKED` 比用不合格数据制造一个漂亮内部指标更有价值。

## 11. 多行合同补充审计（2026-09-05）

对CRDLD的train 1,250张、validation 250张、test 430张标签逐张解码，并在归一化高度
`0.25/0.40/0.60/0.80`统计横向中心线交点。结果如下：

| 划分 | 标签数 | 解码失败 | 存在多行信号 | 任一审计横线最大交点数 |
|---|---:|---:|---:|---:|
| train | 1,250 | 0 | 100% | 7 |
| validation | 250 | 0 | 100% | 11 |
| test | 430 | 0 | 100% | 7 |

在更接近机器人的 `y=0.80` 横线上，以中心±0.04作为“作物行压到相机中心”的保守排除带：

| 划分 | 中心附近存在作物行 | 左右两侧都有行 | 可定义无中心作物行的走廊代理 |
|---|---:|---:|---:|
| train | 50.3% | 74.5% | 40.1% |
| validation | 22.0% | 98.8% | 77.6% |
| test | 49.3% | 86.3% | 46.7% |

标签能够支持“固定评价横线上的所有可见行交点”学习。但标签把所有中心线合并在同一张有损JPEG
二值掩膜中，没有逐行实例ID；各条线还会在远端汇合并在图像边界提前消失。因此不能直接把
连通域数量当作作物行数量，也不能未经派生匹配就报告正式实例检测指标。

Day63重构采用以下受限规则：在预先固定的多条水平带提取交点，按从左到右的拓扑顺序进行
一对一匹配；方向只评价能在至少两个评价带保持身份的行。标签审计结论为：

数据没有显式走廊或机器人车体标注。只有“左右都有行且中心排除带没有作物行”的子集允许
构造相机中心走廊代理；其余帧必须对走廊输出降级或拒绝，不能跨过中央作物行选择更外侧两行。

```text
DAY60_MULTIROW_SIGNAL_SCOPED_PASS
INSTANCE_IDS_NOT_AVAILABLE
DERIVED_ORDERED_MATCHING_REQUIRED
FULL_DATA_GATE_STILL_BLOCKED
```
